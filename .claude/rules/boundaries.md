# Business rules and boundaries

Each rule below is stated once, followed by what breaks it. `pnpm verify` enforces the ones a static check can catch, through the rules in `.dependency-cruiser.mjs` and the checks in `.github/scripts/`; review enforces the rest. A check applies to every file it covers, with no list of exceptions.

1. **Every change of data goes through a use case.** An operation that changes data, in the cloud or in the register's core, is a use case of `packages/domain` reaching storage through ports (see "Operations" below). A cloud route handler and a register core request handler (`*-requests.ts`) only translate their transport and wire the use case; only an adapter imports the database driver or schema as a value; a handler may name their types to hand the connection to its adapter. Breaks it: a route that updates a table itself; a request handler that opens a transaction. Guarded for route and request-handler files only as far as their value imports of the database driver or schema; what a handler does with the connection it hands to an adapter is reviewed.
2. **Reads go through read ports.** A read is a port whose operations are named for their business meaning, implemented by an adapter, never a query written in a route file. Business meaning — active, pending, open, current, valid now, who may see what — is a domain predicate the adapter applies, never a condition invented where the query is written. An adapter may narrow the candidates it hands a domain predicate by criteria that carry no business meaning — the rows with the newest stored date per key, the records a key links to, the ancestors a tree's parent links reach — as long as the predicate still decides over what remains and would decide the same over the full set. A use case that reads data another concept owns declares a narrow read port in its own concept's `use-cases/`, named for what it needs in its own terms, since it never reaches another concept's use cases or their ports. The owning concept's adapter implements it, applying the owner's domain functions, reached through the owner's `index.ts`, and never re-implementing a rule of the owner; the port itself carries no rule of the owner. When the read must see the same transaction as the use case's own writes, the use case declares it as an operation of its own transaction port instead of a separate port; the adapter of that transaction, in the reading concept's folder, hands the operation to the owning concept's adapter code, which runs it on that same transaction and applies the owner's domain functions as the adapter of any narrow port does. A narrow port whose shape partly repeats the owner's own port is a port shape, not a copied rule. Breaks it: `where(eq(products.active, true))` written in a route to mean "sellable"; a list route that filters by the session's permissions itself; the adapter behind another concept's narrow port comparing a code's expiry with `now()` in its query instead of applying the owner's validity function; the replenishment transaction's adapter querying fiscal's deferred sales itself instead of handing the read to fiscal's adapter code. Guarded for route files as in rule 1, and for a use case reaching another concept's use cases; the meaning of a condition is reviewed.
3. **Derived states are answered by the domain.** Whether a promotion is running, a code has expired, the register is locked to the person who opened it, an action needs authorization, or what a person may do, is computed by the domain and answered by the cloud or the core. A screen never computes it and never decides with its own clock. Breaks it: a screen comparing a promotion's dates with `new Date()` to show "Vigente"; a screen deciding from the role's name whether to show an action the cloud would refuse. Reviewed.
4. **Screens make no business decision.** A screen asks the cloud or the core and imports nothing from `packages/domain` but types, neither directly nor through `packages/contracts`, which re-exports no domain value. Parsing and formatting a typed or shown amount is presentation: the parsing lives in `packages/ui`, and the Argentine Spanish formatting of shown text lives in `packages/formatting`, which screens reach through `packages/ui` and the cloud uses directly for the documents it prints. Breaks it: a backoffice screen importing a domain function to decide whether a price may be edited; `export { isOpenSession } from "@purosur/domain"` in `packages/contracts`. Guarded for the backoffice and the register's renderer, and for re-exports in `packages/contracts`.
5. **`packages/contracts` holds wire shapes only.** It describes what crosses a process boundary and imports from `packages/domain` the rule a shape applies; it defines no rule of its own. A check across several fields that is not a domain predicate is a domain rule still missing. Policy values — timeouts, lockout attempts, limits, catalogs such as the alert catalog — are rules and live in the domain's `model/`, never in the cloud, `packages/contracts` or a screen. Breaks it: a `superRefine` in a contracts schema comparing two dates with its own logic; a lockout attempt count declared in a cloud file. Reviewed.
6. **One rule, one place.** A rule found in two layers is a defect: the copy goes, and every layer imports the rule from where it lives. New logic first looks for an existing domain predicate that already answers it. Breaks it: a backoffice helper re-implementing how a discount applies to a price the domain already computes. Reviewed.
7. **`packages/domain` holds business rules and use cases only.** No parsing of typed input, no display formatting, no cryptography or transport parameters, and no limit taken from a column's type without a business reason. Breaks it: a domain function that turns `"1.234,50"` into cents; a name length limit that exists only because the column is `varchar(255)`. Its imports are guarded (it reaches nothing outside itself); the rest is reviewed.
8. **A rule belongs to its concept.** A rule lives in its concept's folder; another concept uses it through that concept's `index.ts`, and a rule more than one concept needs lives in `packages/domain/src/shared/`, reached only through its own `index.ts`. A shape more than one concept in `packages/contracts` needs lives in `packages/contracts/src/shared/`, reached only through its own `index.ts`. Breaks it: `pricing` importing `catalog/model/net-content.ts` directly; `packages/contracts/src/sync/` importing a file of `packages/contracts/src/pricing/`. Guarded in `packages/domain` and `packages/contracts`.
9. **Authorization comes before the data.** Every check that needs no data (a valid session, a fresh authorization when the operation requires it, the permission) runs before any query. Scope (own records, branch) is a filter of the query, never a check after the lookup. Validating the input's shape, which reads no data, may come first. Breaks it: a route that looks up the target user and answers 404 before checking the fresh authorization the operation requires; a use case that loads a record by id and then compares its branch with the session's. Reviewed.

# Operations

An operation that changes state is split in three, each owning one kind of rule:

- **Use case.** One file per operation in its concept's `use-cases/` folder in `packages/domain`, named for what it does (`create-product.ts`). It receives the input the caller already validated for shape, applies the business rules, and returns a union of outcomes naming every way the operation can end; an expected refusal is an outcome, never a thrown error. It reaches the outside world only through ports, and applies the rules of its concept's `model/`. A concept's use cases and ports are reached only through its own `use-cases/index.ts`, exposed as the package subpath `@purosur/domain/<concept>/use-cases`, never through the concept's or the package's `index.ts`.
- **Ports.** Interfaces declared beside the use cases, one per thing the operation needs from outside: storage, the clock, id generation. A port's operations are named for their business meaning (`lockLeafCategory`), not for a table or a query, and no driver detail crosses it: no SQL state, constraint name or ORM type. A read of data another concept owns is a narrow port of the reading concept, as rule 2 states. A failure the use case must react to, such as a write that loses a unique-index race, is an error defined in the domain that the adapter raises. Storage is reached through one transaction per operation, and the order the use case takes its locks in is part of the rule it states. An operation that must keep a record of what it is about to send to an external service commits that record in its own transaction before the call, and records the answer, with everything the answer changes, in a second one after it; the lock that serializes those calls is held across both.
- **Adapters.** The app provides the implementation behind each port in its own concept folder (the cloud's Drizzle store in `apps/cloud/src/catalog/`); the adapter behind a narrow port that reads another concept's data lives in the folder of the concept that owns that data, and so does the code behind such a read declared on the reading concept's transaction port, which that transaction's adapter only hands the read to. An adapter translates driver errors into the port's errors and owns storage concerns such as a missing row being "not found". A cloud route handler or a register core request handler only translates its transport to and from the use case: it parses the request, calls the use case, and maps each outcome to its response.

Each level's tests own what only that level can prove:

- Use-case tests run against in-memory fakes of the ports, kept in the concept's `use-cases/test-support/`. They prove every rule and every outcome, including the lost race, the rollback of a failed operation, and the order of the locks.
- What only a real database can prove (locks, concurrency, constraints, the result of a query) is owned by the adapter's integration tests and by the route tests against the database.
- A route test proves the wiring: authorization, that the route reaches the use case, and the response of each kind of outcome.
