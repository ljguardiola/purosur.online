# Releases

The cloud service and the register app are two independently versioned deliverables: `cloud-vX.Y.Z` and `pos-vX.Y.Z`. A merge to `main` that changes the cloud deploys it to staging automatically once its Verify run passes; one that changes the register or a package it uses builds the register's staging installer, kept as an artifact of that run. A register release is named after its installer's version, `pos-v<major>.<minor>.<run number>`: the major and minor come from `apps/pos/package.json` and the run number from the packaging run on `main` that built the installer staging serves, so patch numbers skip between releases. Its promotion attaches that production installer, `Puro Sur Setup <version>.exe`, to the release.

Promoting a cloud release runs the route tests of the release production serves against the schema the new release migrates to, so production keeps working while the deploy swaps it, and any failing test stops the promote. The promote's `declared_breaks` input names, as a JSON array of `"<file> > <test's full name>"` strings written as Vitest prints them, the tests the new release breaks on purpose; the promote then goes ahead when only declared tests fail, and its log lists each declared test with whether it failed or passed. A test is declared only when the new release changes the rule it checks on purpose, and only when the registers enrolled in production are left unused while the deploy runs, since until it ends they may reach the previous release running on the new schema.
