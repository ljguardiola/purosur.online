# Review checklist

Each area names where its rules are written and what part of the change to
read against them. Read the cited sections in full: the rules are there, not
here. A finding cites the written rule it breaks or the issue's
definition-of-done item; a finding that can cite neither is a correctness
finding or is not a finding.

| Area | Rules written in | Read in the change |
|---|---|---|
| Issue scope | `issue.md` in the review folder | Each definition-of-done item against what the change delivers, and anything the change does beyond the issue; an example the review itself added to this checklist is not work beyond the issue. Examples: a path-scoped rule file that another rule file sends to, where the two files' `paths:` do not overlap; a file split by topic that still holds two unrelated former sections under separate top-level headings; a path-scoped rule whose trigger can happen without reading a matching file (such as `pnpm add` changing a `package.json`); a definition-of-done item delivered only for the forms a check recognises by name, such as runtime module loading handled for a bare `require(path)` but neither refused nor recognised as `createRequire(import.meta.url)` or `globalThis.require`. |
| Correctness | — | What the changed code does with each input it can receive; code left without a reader by the change; tests that would still pass with the behavior they name removed. Example: a message the core now checks against a stricter contracts shape than the reader it replaced, so stored data that reader accepted (such as installation keys the domain refuses, read back from a corrupted credentials file) gets a different outcome; a static check that misses a place its input can take, such as a query key given as a parameter's default value, passed as a JSX attribute or fed to a typed callback; a static check that follows a function's callers by its declared name only, so the same function handed on uncalled under another local name escapes it (renamed or default import, renamed re-export, destructured property, `obj.fn` passed as a value); a static check that follows a function's references and counts any reference that is not a value use as an unchecked caller, so a JSDoc `{@link fn}` or `@see fn` mention, the method signature of an interface the object is typed with, a string-literal access (`obj["fn"](…)`, `(typeof obj)["fn"]`), or another object literal typed with the same interface that declares its own method makes it refuse a key whose only calls it checks; a check of a folder convention that treats every top-level folder as a concept, accepting in `shell/` or `platform/` what it refuses at the source root; a guard no input can reach, such as a check for a reference inside a type argument placed after a walk that already returns at that TypeNode; a static check that counts an interface's member signature as a checked caller while the call through that interface resolves to the interface's parameter type, so `invalidate(key: readonly unknown[])` in the interface, implemented with `key: QueryKey`, leaves `obj.invalidate(["other"])` unchecked; a check that lets a value pass through unless it finds an escape (fail-open), so every unforeseen route — JSX children, a destructuring assignment with a default, or a module reached as an object through a barrel's named re-export or Vite's `import.meta.glob` — escapes it, where a fail-closed rule accepting only a few recognized shapes would refuse it; a static check that marks a module reached from any mention of its path (a type-only `typeof import("./x")`, a side-effect `import "./x"`, a `vi.mock("./x")` in a test file it leaves out), so it refuses a key whose only calls it checks. |

## Commit order

Each commit in `commits.patch` lists its files under its message, then its
diff. A moved or renamed piece of code shows as a rename in that list, or as
removed in one file and added unchanged in another; a change that keeps
behavior leaves what every test of the touched files asserts as it was.

A behavior commit with no earlier test commit of that behavior is a `rule`
finding that names the commit's short sha and the behavior, as an input and
its outcome. It is resolved as the commit-order rule in `.claude/rules/code-style.md`
("Code style") says, so a re-review does not reopen it because the history
still shows the code first.

## Kinds

- `rule`: the change breaks a written rule. Fixed.
- `correctness`: the change behaves wrongly for an input it can receive, or leaves code no reader uses. Fixed.
- `scope`: a definition-of-done item the change does not deliver, or work beyond the issue. Fixed by delivering it or removing the extra work.
- `decision`: the change replaces or drops a library of the confirmed stack, adds a library for something the stack already covers, or contradicts a written rule on purpose (applied across the change, or a choice its pull request would state under "Technical decisions"). Adding a library the stack names is not a decision. The review stops on it.
